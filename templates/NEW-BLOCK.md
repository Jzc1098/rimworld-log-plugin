# 新块该写的说明

**本文件是模板。写新块时复制它，或者照着它的结构写注释头。**

---

## 为什么值得写

这个项目里的块大多带一段注释头，而它们**不止一次救过场**：

- `lib/blocks.mjs` 里关于「为什么两处扫描器是 bug 的根源」那段注释，解释了为什么不能把它们再拆开
- `fix-vf-turretqueue-save` 的描述里写着「不能改成 `LookMode.Value`」——而那正是第一版犯的错
- `apply-mod-change` 附近注明了「游戏运行时拒写」，避免了「为什么写了没生效」的重复排查

**判断标准很简单**：如果这个块将来被别人改，**哪一句话能让他不踩坑**，就写那一句。

---

## 模板

```js
/**
 * 一句话说明这个块做什么。（祈使句或名词短语，不要「这个函数用于…」）
 *
 * 为什么需要它
 *
 * 它解决的具体问题。若能引用一段真实日志或一段错误堆栈，就引 —— 具体的证据比抽象的说明有用得多。
 *
 * 为什么这样做而不是那样做
 *
 * 列出考虑过的替代方案以及被否掉的原因。这一段最重要：它挡住「看起来更简单的改法」。
 * 若某个写法会出错，直接写「不要那样写，因为…」。
 *
 * 注意事项
 *
 * 边界条件、并发、性能、副作用。
 *
 * @param name - 含义、取值范围、为 null 时会怎样。
 * @returns 返回什么；可能为 undefined 的条件。
 */
```

**不是每段都要写。** 一个五行的辅助函数只需要第一句。**但「为什么这样做而不是那样做」只要存在替代方案，就该写。**

## 引用证据的写法

**这个项目的注释里，最有用的是带具体数字和原文的那些。**

好：

```js
/**
 * CE 在「穿透 ÷ 护甲 < 0.5」时把伤害清零。而反应堆爆炸的穿透恰好是 0 —— XML 里没人写
 * armorPenetration，字段默认 -1，TimedExplosion.Data 兜底成 Flame.defaultArmorPenetration，
 * 而原版 Flame 就是 0。实测：同一部件命中 83 次，血量恒定在 3.112842（小数点后 6 位不变）。
 */
```

差：

```js
/**
 * 修复载具伤害计算错误。
 */
```

**前者能让人判断这个修复是否仍然需要；后者什么也判断不了。**

## 写不写「不知道」

**要写。** 明确标出不确定的部分，比含糊其辞或编一个理由都好。

```js
/**
 * 性能：只在列表长度 > 1 时做快照。
 *
 * 未实测验证：这是基于 List<T> 的枚举器 _version 语义的推理 —— 长度 ≤ 1 时 Clear() 后 Add()
 * 落在同一索引，不会让枚举器越界。若崩溃复现，这里是第一个要检查的地方。
 */
```

**这段「未实测验证」比整段优化的理由都值钱** —— 它告诉后来者该怀疑哪里。

## 子版本号与署名

**不用手写。** 写完代码跑一次：

```bash
node tools/stamp-blocks.mjs
```

它会：
- 给新块分配 `1.1.0.<你的名字>.003` 这样的子版本号
- 给改过的块记下 `modifiedBy` / `modifiedVersion` / `modifiedDate`，**同时保留原作者**

**块与块之间的关系**（改名、取代、变体、互斥）要在 `blocks.json` 里手写那四个可选字段 —— 那部分工具不会覆盖。含义见 `templates/blocks.example.json`。

## 自检清单

新块写完、提交之前：

- [ ] 跑 `node tools/stamp-blocks.mjs` 并确认新块被登记
- [ ] 跑 `node tools/selftest-blocks.mjs`（若改过切分器或 `lib-blocks.mjs`）
- [ ] 跑 `node tools/selftest-plugin.mjs`（若改过 `index.js` 或 `plugins/`）
- [ ] 若改了块之间的关系，补上 `aliases` / `supersedes` / `variantOf` / `conflictsWith`
- [ ] **若改了 `index.js`：重启 DSH** —— 模块缓存键是「包」不是「行」，热替换无效
